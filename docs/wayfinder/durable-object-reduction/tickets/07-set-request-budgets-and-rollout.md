## Question

What measurable traffic/storage budgets, quota-error behavior and migration checks must the eventual implementation satisfy?

Choose targets from the measured baseline, including idle agent-hub calls, rows read/written, active duration and retained bytes. Define backoff and suspension when a daily allowance is exhausted, manual recovery and reconnect behavior, authentication-only reads, and observable failure states. Specify safe migration from stored agent mirrors to browser state, preservation of existing sign-in and drafts, and local/preview/production validation. A paid upgrade is a separate user decision, not an automatic mitigation.

## Context

The [quota baseline](../research/quota-baseline.md) observed 95,517 account DO requests on 2026-10-15, close to the published conditional Free allowance. Neither the original exhausted dimension nor the actual billing plan was verified. Use scenario counters and completed comparable production windows; do not promise a savings percentage or treat analytics sampling-derived counts as exact billing counters. The [relay research](../research/live-relay-and-cleanup.md) establishes that continuously pending DO HTTP handlers can prevent hibernation, so eliminating storage polling alone does not make continuous remote watching cost-free.

## Answer

- Remote-off startup, menu opening and idle visible/hidden tabs generate zero agent-hub calls, context uploads or remote-agent storage writes. Normal authenticated editor/GitHub traffic is accounted for separately. Idle remote connections must remain hibernation-compatible, without periodic snapshots or storage heartbeats.
- Quiet waiting is the default; stop unattended repeat-until-work loops. Explain that users may need to resume a third-party agent themselves. Offer explicit Watch mode for at most ten minutes per activation, with a visible deadline, then pause. Empty results and ordinary commands cannot renew it. Measure its request/duration cost separately from idle hibernation.
- A positively identified daily quota-exhaustion response pauses automatic remote reconnects, waiting, uploads and retries. Preserve sign-in/drafts, show a clear paused state and a known reset time if available, and allow one controlled manual recovery attempt while respecting authoritative Retry-After. Do not relabel generic network/auth failures as quota exhaustion or bypass authorization. Local operations independent of the exhausted service may continue. No automatic paid upgrade or offline mailbox.
- Give ordinary relay commands a ten-second total deadline. Watch permits one outstanding wait per workspace, at most 25 seconds each (clipped to remaining Watch time), and at most 25 waits per ten-minute activation. Count this across tabs/grants; only explicit user renewal resets it. Watch expiry stops new waits without revoking the connection or silently cancelling a separate edit. Remove transient payloads at terminal events and reconcile unknown edit outcomes. Require zero storage-poll reads and zero persistent content mirrors; instrument the proposed four-invocation control path separately from initialization, WebSocket messages, GitHub fetches and lifecycle metadata.
- Coordinate transient-network reconnects through one workspace owner: at most five attempts over two minutes, exponential backoff starting at one second with jitter, then pause. Respect authoritative Retry-After, sharing the budget across tabs/grants. Do not replay mutations or re-arm quiet/expired Watch loops. Authentication/revocation and daily quota failures follow their distinct recovery paths. Manual Retry is single-flight and respects cooldowns.
- Validate instrumented local scenarios, then the separate preview deployment, before production. Cover idle visible/hidden, quiet connected idle, Watch, edits/reads/reconnect, duplicates/unknown results, network/quota/storage faults, handover/freeze/restart and cleanup races. Require preserved drafts/sign-in/configuration, accepted caps, modern/legacy cancellation handling and authentication-only reads that do not load repository caches. Compare all metered dimensions with consistent scenarios and distinguish migration/Watch/steady operation. Investigate unexplained regressions; no unsupported savings percentage or automatic production deployment.
- Inventory legacy objects through cursor-paged namespace discovery and sanitized classification before deleting. Remove only identified, eligible temporary/expired records after browser recovery, presence, deadline and generation checks. Preserve configuration, sign-in, active registrations and unexpired one-time authorizations. Re-enumerate after a pass and report redacted scanned/classified/deleted/deferred/unknown counts. Unknown or inaccessible records need review; discovery gaps prevent a claim of complete cleanup.
- Start legacy cleanup with ten canary objects, then up to 100 objects per batch. Limit migration to 1,000 maintenance DO invocations per namespace per UTC day, including inspection/deletion/nested calls, and a conservative 5,000 written-row daily budget only after preview accounting can bound the next deletion. Defer unbounded/oversized work rather than assuming free deletion. Resume from protected checkpoints; pause on quota failure and do not automatically raise limits. These migration budgets do not replace ordinary lifecycle cleanup. Remove temporary inventory material after reporting/verification through the normal cleanup workflow.
- Use independent remote-relay, Watch and modern-registration controls. On regression, pause affected remote features and cleanup, preserving browser data, sign-in, manual editing, schema compatibility and generation fencing. Never restore a release that restarts polling, mirrors draft contents or replays unresolved operations. Reject obsolete endpoints before DO work after cutover and provide upgrade/reconnect guidance; stale tabs can still consume Worker requests until refreshed, which must be measured separately. Resume after failed checks pass and compare comparable completed production windows. Record a recurring quota error accurately; the historic exhausted dimension remains unverified.

Lex accepted the three traffic/recovery proposals with "ok", the three limits/release-gate proposals with "Yes", and the final three migration/rollback proposals with "Ok". All planning decisions for this ticket are resolved. See the [implementation handoff](../handoff.md) for dependency order and runtime gates. This resolution does not deploy or implement the application.

## Static per-call evidence

A scoped source investigation of `worker/agent-context.ts`, `worker/app.ts`, `worker/mcp.ts` and `worker/agent-store.ts` found three authentication DO invocations per already-used MCP grant: grant, sign-in session and hub. First use adds two initialization calls. A simple state read adds one hub call; draft reads can add more. Changed edits add queue work plus approximately 25 result polls over ten seconds. An empty default 25-second wait performs approximately 18 hub operations, roughly 21 DO invocations including authentication, and currently instructs the client to repeat. Browser polling/acknowledgements add separate traffic. These are code-path counts/estimates, not measured production traffic or SQLite row counts.

The proposed event-driven control path should target at most four DO HTTP invocations per already-authorized bounded call (three retained auth checks plus one dispatch), with first-use calls and WebSocket messages accounted separately. Multi-file/GitHub data fetches, explicit connection lifecycle/receipt reconciliation and initialization have separate attributed budgets; the target must not be misrepresented as a bound on every whole workflow. The implementation must demonstrate the path with instrumented scenarios before claiming the target is met.

## Legacy discovery evidence

The [Cloudflare object-list API](https://developers.cloudflare.com/api/resources/durable_objects/subresources/namespaces/subresources/objects/methods/list/) supports cursor pagination and returns object IDs plus `hasStoredData`, not original names, kinds or expiry. A documentation-only investigation found accepted read permissions, but actual account permission has not been tested. IDs must not be classified by a presumed name prefix; [DO identifier documentation](https://developers.cloudflare.com/durable-objects/api/id/) explains that names are hashed and `idFromString()` does not recover the original name.

Use a restricted, separately authorized maintenance path that classifies each object's internal records and returns only kind, expiry, eligibility and generation, never credentials, config secrets or draft contents. Ordinary session GET is unsuitable for sanitized inventory. Checkpoint the deployment/namespace, opaque cursor/object IDs, batch status and scan time in a restricted maintenance manifest; do not create a new indefinite global DO mirror. Recheck expiry/presence/generation at deletion, repeat enumeration after a pass because snapshot consistency is unproven, and report scanned/classified/deleted/deferred/unknown counts. Missing permissions or unknown records forbid claiming complete cleanup.

SQLite `deleteAll()` is appropriate only for an isolated object's fully disposable contents and removes the database atomically; per-key deletion writes rows. Checked [storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) and [pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) documentation does not establish a reliable per-object `deleteAll()` row charge for this migration. Do not assume deletion is free or infer write cost from draft byte size; verify accounting with instrumented preview canaries before bulk cleanup. Every cleanup HTTP/RPC/alarm invocation still needs its request accounting.

Watch preserves a smoother active workflow but consumes requests/active duration and must be measured separately from idle hibernation.
