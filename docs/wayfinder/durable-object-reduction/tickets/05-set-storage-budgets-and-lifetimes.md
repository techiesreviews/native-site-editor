## Question

Which records may persist in Durable Objects, with what hard size/count caps and cleanup rules?

Inventory login sessions, agent permissions, OAuth clients and one-time records, registration limits, repository caches and legacy agent mirrors. Decide individual and aggregate caps, maximum lifetimes, overflow behavior and cleanup of already-existing records. Preserve App configuration and sign-in; do not treat a repository cache as required durable user data. Specify how cleanup consumes quota and how session expiry, grace deadlines and alarms interact.

## Answer

- Persist no agent draft, context, command-body or conversation copies in Durable Objects. Keep at most five agent connections and 64 KiB of aggregate persistent agent metadata per workspace, including attributable records in separate objects. Reject additions clearly before allocation when either cap would be exceeded.
- Use a memory-first repository-list cache with a durable fallback capped at 256 KiB per sign-in session. Oversized listings still work through normal GitHub fetching. Load the cache only when needed, not during authentication-only reads; refresh on demand.
- Keep that bounded durable cache until sign-out or sign-in expiry, then request deletion. Do not use the proposed fifteen-minute retention deadline or a periodic keepalive. Cache retention does not relax authorization freshness or extend sign-in.
- Adopt CIMD as the long-term direction for compatible MCP clients, retaining dynamic registration for compatibility. Compatibility and reconnect behavior must be verified before rollout or shortening fallback registration retention. The proposed thirty-day inactivity deadline remains conditional, not an accepted hard cutoff. Keep this work behind the primary polling/request reductions, without changing GitHub sign-in or the five-minute agent permission cleanup contract.
- Keep OAuth authorization requests for at most ten minutes and authorization codes for at most five minutes; consume one-time records and request deletion after use. Expired records are unusable even if physical cleanup runs later.
- Keep the existing 1 MiB text-file limit. Admit at most five pending relay commands and 8 MiB of total serialized buffered relay payload per workspace. Return a clear busy/too-large error when full, without persisting the payload. This bounds application payload admission, not total runtime memory.
- Cap dynamic-registration metadata at 16 KiB per record and 10,000 retained registrations per deployment/namespace. Preserve current registration admission rates: ten per IP/hour, 100 globally/hour and 1,000 globally/day. At capacity, refuse new registrations clearly and preserve existing ones. Counters/indexes and physical storage overhead are additional to these metadata bytes. Account for creation/deletion failures idempotently; inventory legacy registrations before claiming an aggregate bound covers them.
- Cap unfinished OAuth authorization requests plus codes at 20 records and 64 KiB of serialized record data per sign-in session. Reject additions clearly at capacity; do not evict existing pending authorizations or extend their deadlines. Allocate, consume and expire with idempotent accounting, without adding writes to normal tool traffic.
- Disable old content writers before migrating legacy agent copies. Use quota-bounded cleanup batches and cleanup on access. Confirm browser draft recovery before deleting live-workspace copies; otherwise surface recovery and defer deletion. Do not replay legacy pending commands; treat their outcome as unresolved and require fresh authorization after grant removal. Apply the accepted five-minute disconnect grace and absolute expiry backstop while preserving sign-in, browser drafts and App configuration. Inventory discoverable objects and explicitly report any unknown/unreachable records. The rollout decision owns discovery and batch mechanics.

The final three shared-storage proposals below were accepted by Lex ("ok"). These are product budgets, not measured demand or Cloudflare limits. All application implementation remains pending. The long-term registration compatibility findings and resulting fallback lifetime/rollout choice are tracked separately in [Establish modern registration compatibility and safe metadata lookup](08-research-modern-registration.md) and [Choose registration compatibility and retention rollout](09-choose-registration-rollout.md); the proposed thirty-day inactivity cutoff is not silently enabled by this storage decision.

- Next retention round, pending acceptance:
  1. Expire the durable repository-list cache 15 minutes after its last successful refresh, or at sign-in expiry if earlier. Cache reads do not extend retention. Refresh only on demand; stale retained data must not bypass the existing maximum 60-second authorization freshness or fresh checks required for writes. Use logical expiry on reads and the object's combined alarm schedule for eventual physical deletion; do not introduce periodic cache keepalives.
  2. Preserve the existing ten-minute OAuth authorization-request and five-minute authorization-code lifetimes. Consume one-time records atomically and request deletion after consumption; reject expired records immediately even if physical alarm cleanup is delayed.
  3. Preserve the existing 180-day maximum lifetime for OAuth client registrations (application identity and redirect metadata), separately from workspace grants. Registration alone provides no repository access and must not extend the accepted five-minute agent cleanup period. Registration size/count limits remain a separate decision. This favors avoiding unnecessary client re-registration; it does not retain draft content or workspace permissions for 180 days.
- Lex requested the impact of cache expiry and whether easier setup would allow shorter registration retention. None of the retention-round proposals is accepted by that question. Cache expiry removes a rebuildable listing, not drafts or sign-in; a subsequent cache miss needs GitHub fetching and may add latency/API traffic. Retention is distinct from authorization freshness. Alarms and cleanup consume quota, so use the combined deadline schedule rather than a recurring fifteen-minute refresh/cleanup loop; shorter retention does not itself establish lower daily request usage.
- Registration investigation: `worker/oauth.ts` currently creates random `mcp_…` identifiers, retains metadata for a fixed 180 days and tells users with expired/unknown clients to remove and re-add the connector. Merely lowering `CLIENT_LIFETIME` therefore risks more setup interruptions. The [2026-07-28 MCP client-registration specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration) recommends Client ID Metadata Documents (CIMD) and retains dynamic registration for compatibility. With CIMD, a supporting app supplies its HTTPS metadata URL; the server validates metadata and redirect URIs and can use a bounded rebuildable cache instead of allocating a durable registration per client. This project does not currently implement CIMD, and support in the actual target clients has not been verified.
- Revised registration direction, pending acceptance: evaluate CIMD for supporting clients while retaining dynamic registration as a fallback; propose a 30-day inactivity lifetime for fallback registrations, renewed only by successful user authorization, with retention writes coalesced to at most once per day per registration. Ordinary tool calls, unauthenticated requests and denied authorization must not extend registration retention. Keep user consent, PKCE, workspace grants and five-minute agent cleanup separate. Before shortening lifetimes, verify reconnection/re-registration behavior in each target client; expired identifiers must never be accepted or redirected to unvalidated callbacks merely to improve recovery. Provide a guided reconnect path, acknowledging that a third-party app may still require removal/re-addition. Exact compatibility fallback policy, metadata fetching safeguards, count/byte caps and legacy migration remain unresolved. This direction does not change GitHub sign-in architecture or authorize implementation.
- Accepted by Lex on 2026-10-17 ("1. let's do what you suggest" and "we can implement it if it's better long term"): replace the fifteen-minute cache retention proposal with retention until sign-in expiry, deleting on sign-out as well; take modern client identification forward as a long-term improvement subject to actual compatibility evidence. Preserve the Wayfinder-first scope: this is authorization for the eventual direction, not an instruction to begin application changes before the remaining plan decisions. The earlier 180-day retention recommendation and thirty-day inactivity alternative have not established a new accepted fallback lifetime.

- Final shared-storage proposals, pending acceptance:
