## Question

What must the browser persist before acknowledging an agent edit, and what can safely be replayed after reload or reconnect?

Settle draft and receipt transaction boundaries, command IDs and expected versions, lost acknowledgements, duplicate delivery, cancellation, stale connection generations, browser quota failures and multi-tab ownership changes. Decide how Ask agent conversations and immutable repository content are recovered and evicted. Define what the agent sees when a local record is unavailable; browser-local storage does not imply cross-device recovery.

## Answer

- Commit an agent edit's draft changes and edit receipt together before reporting successful local application. Multi-file commands commit all changes or none. This is browser persistence, not a GitHub save or a guarantee against subsequent browser storage eviction.
- Reconcile a lost response by operation identifier and payload identity. Return a matching recorded outcome without applying the edit again. Reject reuse of an identifier for different work. Without a receipt, the outcome is unknown and must not be replayed automatically. Recheck workspace authorization before revealing recorded results.
- If browser persistence fails or is unavailable, refuse the agent edit clearly and preserve existing drafts. Offer recovery/export rather than a silent Durable Object fallback. This does not change the manual editor's existing persistence behavior.
- Retain completed edit receipts locally for up to 24 hours, capped at 1,000 receipts and 1 MiB of serialized metadata per account/repository/branch workspace. Evict oldest eligible completed receipts first, never unsaved drafts. Expired/unverifiable operations remain unknown and cannot be replayed automatically; generation/identity/revision checks must prevent late delivery from becoming a fresh edit after receipt eviction. Refuse new edits before mutation if a required receipt cannot fit safely.
- Store Ask agent questions/replies in the browser, isolated by workspace. Retain completed conversations for up to seven days within a 1 MiB serialized conversation budget. Keep at most 50 unfinished requests within that same budget, preserving them until resolved/dismissed rather than silently evicting them; reject additions clearly at capacity. History does not restore grants and is not shared across devices or guaranteed after browser storage loss.
- Explicit tab takeover pauses new agent edits, reconciles outstanding outcomes and loads current drafts before transferring ownership with a new generation. Unknown operations remain unknown. Commit-time fencing must reject late edits from the previous owner, including after freeze/resume. Background owners retain ownership; focus alone does not transfer it. Expected revision checks reject stale agent edits that would overwrite newer manual changes.
- Cancellation that wins before the edit transaction commits prevents application. After commit, report that the edit was already applied to the local draft; do not silently undo it. Reconcile uncertain outcomes against receipts or report unknown. Transport loss alone does not prove cancellation. Serialize ownership/revocation checks against the commit boundary so work cannot apply after a completed transfer or revocation.
- On browser quota failure, evict rebuildable source caches and eligible completed history/receipts before retrying an uncommitted transaction at most once. Reconcile uncertain transaction outcomes before retrying. Preserve unfinished requests, unsaved drafts and associated uploads. If persistence still fails, stop agent edits, show an actionable error and offer export of available unsaved drafts and associated uploaded bytes. Never clear unsaved work without explicit user action or claim recovery of already-lost/inaccessible browser data.
- Do not add a persistent mirror of unchanged GitHub source. Use a disposable in-memory cache capped at 32 MiB per tab, keyed by account/repository/immutable revision/path, evicting least-recently-used clean content first. Clear private cached source on sign-out/account change. Missing clean source is fetched again with current authorization checked before private content is exposed. Preserve draft baselines and uploaded bytes required for unsaved-work recovery separately from the disposable cache. Full offline editing and cross-device recovery remain outside scope.

Lex accepted each of the three recovery rounds with "ok". The contract is complete; browser transaction/failure, late-command and freeze/resume tests belong to the rollout decision. No application changes have been made for this ticket.

## Comments

- First recovery round, pending acceptance:
  1. A successful agent edit means its draft changes and an edit receipt have committed together to browser storage. A receipt identifies the operation, account/repository/branch, ownership generation, expected input revision and resulting draft revision; it need not duplicate file content. A multi-file command is one all-or-nothing commit. The existing delayed draft flush alone is insufficient to establish this acknowledgement contract. This is a local commit, not a GitHub save or a guarantee against later browser storage eviction.
  2. If a response is lost, reconcile the same operation identifier and payload identity against the browser receipt. Return the recorded outcome for a matching completed operation without applying it again; reject identifier reuse with a different operation. With no receipt, report the outcome as unknown rather than replaying automatically. Recheck current workspace authorization before exposing an old result.
  3. If browser persistence fails or is unavailable, refuse the agent edit with a clear local-storage error before presenting a successful application. Preserve existing drafts, never silently move the operation into a Durable Object, and offer recovery/export of any existing unsaved work. Manual editing's existing storage behavior is not automatically changed by this agent-edit contract.

- Accepted by Lex ("ok"): all three proposals in the first recovery round. Recorded above.
- Next recovery round, pending acceptance:
  1. Retain completed edit receipts locally for up to 24 hours, bounded by 1,000 receipts and 1 MiB of serialized receipt metadata per account/repository/branch workspace; evict oldest eligible completed receipts first. Never duplicate file contents in receipts or delete unsaved drafts to make room. Receipt eviction ends proof of the old outcome, not a license to replay it: expired or unverifiable retry identifiers return unknown, and old-generation commands are rejected. If bounded accounting cannot admit a new receipt safely, refuse the new agent edit before mutation. Operation identity/generation/revision checks must still prevent late delivery from becoming a fresh command after journal eviction.
  2. Keep Ask agent questions and replies only in browser storage, isolated by account/repository/branch. Retain completed conversations for up to seven days, pruning oldest completed records within a 1 MiB serialized conversation budget per workspace. Keep at most 50 unfinished requests within the same budget; never evict an unfinished request silently to admit another, instead ask the user to resolve/dismiss existing requests or export/clear history. No bulk upload of history to a Durable Object on reconnect. Active questions can outlive seven days until resolved/dismissed, subject to the count/byte cap. Browser history does not restore old grants and is unavailable on other devices or after browser data loss.
  3. For an explicit receiving-tab takeover, pause new agent edits, reconcile outstanding operations against committed receipts, then reload current local drafts and transfer ownership with a fresh generation. Unprovable operations remain unknown. Commit-time ownership fencing must prevent a delayed old tab from applying an edit after takeover, including a frozen tab resuming later. A background connected owner stays owner; merely focusing another tab does not transfer it. Recheck expected draft revisions against manual edits and report a conflict instead of overwriting newer work.

- Accepted by Lex ("ok"): all three proposals in the next recovery round. Recorded above.
- Final recovery round, pending acceptance:
  1. Cancellation that wins before the edit transaction commits prevents application. Cancellation after commit reports that the edit was already applied to the local draft and does not silently undo it. If the result cannot be proven, reconcile the receipt or report unknown; a transport disconnect alone cannot prove cancellation. Revalidate permission/ownership/expected revisions immediately before committing; serialize revocation/takeover against that commit boundary so late work cannot apply after a completed revocation or transfer.
  2. On browser quota failure, evict rebuildable source caches and eligible completed history/receipts first, preserving unfinished requests, unsaved drafts and uploaded files needed by those drafts. Retry the uncommitted transaction at most once after safe cleanup; reconcile uncertain transaction results before any retry. If it still fails, stop agent edits, show an actionable storage-full error and offer a download/export of available unsaved drafts and associated uploaded bytes. Clearing unsaved work requires explicit user action. Do not claim recovery for browser data already evicted or inaccessible. The existing all-or-nothing agent draft/receipt rule continues to apply.
  3. Do not add a persistent mirror of unchanged GitHub source for this mitigation. Use an in-memory source cache bounded to 32 MiB per editor tab, keyed by account/repository/immutable revision/path, evicting least-recently-used clean content first and clearing private cached content on sign-out/account change. Fetch missing clean content normally after eviction or reload, with current authorization checked before private content is exposed. Draft baselines and uploaded bytes required to recover unsaved work are draft data, not disposable clean cache; preserve them. This does not promise full offline editing or cross-device recovery.

- Accepted by Lex ("ok"): all three proposals in the final recovery round. Incorporated into the answer; the ticket is resolved.
