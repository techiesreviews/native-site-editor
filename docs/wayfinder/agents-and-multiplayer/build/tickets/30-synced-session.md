## Goal

People without an account edit with Lex through a link. Stage 3 starts only after stage 2 is released.

## Decided behaviour

[Ticket 07](../../tickets/07-grill-synced-session.md#resolution-2026-10-24) and CONTEXT.md "Synced session":

- Share to edit in the project menu, then Copy edit link, copies a link: a session token plus the key after `#` (labels changed by Lex on 2026-10-27; no Live badge).
- A guest types a name and edits text, pictures and sections on the pages in the session.
- Only Lex saves, publishes, changes files or settings, and uses agents.
- The session lasts while his tab is open; Stop sharing or closing the tab ends it and kills the link. Every share makes a new link.
- Guests' changes become his unsaved changes. Typing shows only the guest's caret, which stays while she is in the session. A styling, picture or look change briefly shows an outline in her colour with her author chip (Lex, 2026-10-27).
- While a guest types, her caret shows in the page text in her colour, and she sees Lex's. It uses the shared caret look from ticket 23 and mock-up 13 (Lex, 2026-10-27: "we see the caret when people are typing somewhere").
- Mock-up approved by Lex (2026-10-27, after his changes): [14-share-live.html](../../prototypes/14-share-live.html)

## Done (2026-11-08)

- Share to edit in the project menu (`src/components/repository-menu.ts` `shareItems`, `src/share-control.ts` `createShareControl`): shown only while a site is open, it starts a synced session on the page shown and copies its link, `/live?s=<token>#k=<key>&site=<name>&by=<login>`. The item itself says "Link copied" for 2.5 s with the menu still open (no toast), read out through `aria-live`; while sharing starts it stays focusable (`aria-disabled`). A copy the browser refuses shows the link in a read-only field to copy by hand. While sharing, the menu offers Copy edit link and Stop sharing, and the guests show by initial beside the project tile, at most three and a "+N", each in the guest colour Lex's tab gave them as they joined (one nobody in the session has, else the least used), sent to the guest pages with each render so every page agrees; `--guest-1`…`--guest-4` in `src/theme.css`, `src/components/person-chip.css`). Every share makes a new token and key. Opening another project or branch stops sharing (`check` after each load); a refusal says "Sign in to share" when signed out and "Couldn't share" otherwise. A menu closed while sharing starts writes nothing.
- The session (`startSharing`, loaded with the first share; a room that has not opened after 10 s gives up, and the menu offers Share to edit again): the Worker mints it for the signed-in tab (POST `/api/live/share`, `liveSessionKeys`): a token of 128 random bits and a tag made with the GitHub App's secret, and the sharing tab's own proof bound to its login and repository, never in the link. A made-up or forged token is refused (400) before any Durable Object wakes, and only the tab holding the proof can hold the room (another sign-in with the link gets 403). Each session has its own relay instance and room, named from the token (`worker/agent-relay.ts` `liveSessionObjectName`). Lex's tab holds it open through `/api/live/share` (editor sign-in, repository access and the proof); guests join through `/api/live/guest` with the token alone, and only while a sharing tab is in (`LiveRooms.admits`: agents and guests both need an editor in the room; only an editor makes a key). The room key travels after `#` and is used as given (`src/live-room.ts` `key` option): no handover, so the server never holds it. When the sharing tab leaves cleanly (Stop sharing, or the tab closing: close codes 1000 and 1001), the relay closes the guests' sockets and the link refuses: a plain request answers 410 "This edit link has ended." (`/live/admits` on the session's Durable Object). When its socket drops instead, the relay tells guests it was lost (`LIVE_HOST_LOST`, 4408): their page waits ("Waiting for <login>…", the frame takes no typing) and joins again every 2 s for up to 30 s, then says the session ended.
- Who sent what: the relay puts the sender's peer id before each frame it forwards (`worker/agent-relay.ts`, `src/live-room.ts` `onMessage`), so guest pages take the page only from the sharing tab and Lex's tab takes a change only from the guest's own socket. Tabs opened before this change cannot read frames in a live room until reloaded.
- What guests are sent: each render of the page on show, with every asset their copy lacks, at most 16 MiB of new assets per message (the rest follow), and the components and stylesheets only when they changed since that copy's last message (`src/components/native-preview.ts` `mirror`); a message still too big is followed by the whole page again, in parts that fit a room frame and in order (`sessionWire`); only the shown page's body, never the site's other pages, and nothing while History shows an earlier version. A guest who joins, or a reconnect, gets the whole page again. With nobody in, no copy is made. While Lex's tab is hidden (no animation frames), a render waiting for guests goes from a timer.
- What guests send: the text typed in their copy, letter by letter; Lex's tab writes it as its own text change (`guestTextEdit` through the page's own text edit path), so it is his unsaved change and his Undo takes it back, one step per guest's typing. Only text of the page on show counts, from a guest listed by presence, well-formed; nothing is refreshed for a change whose write ends after the session stopped. Each render tells every guest how much of their typing is written, so their copy keeps the letters still on their way.
- The guest page (`live.html`, `src/live-guest.ts`, `src/live-guest.css`): "Edit <site> with <login>", a name and Join; then a top bar with the site and who is here (the sharer marked, the guest as "you") over the same sandboxed preview frame the editor uses. It loads the frame and the live room only (about 18 KB gzipped, the room code once joined): no sign-in, Save, files, settings or agents exist there. A join that has not got in after 10 s gives up and offers Join again ("Couldn't join. Check your connection and try again."); only a 410 or the session's end says "This edit link has ended.", and a link the Worker refuses says "This edit link is not valid." A link cut short says "This edit link is not complete."; a page brought back from the browser's cache says the session ended. The preview frame's document moved to `src/components/preview-frame-doc.ts` so both pages use it (the build's runtime bundling follows it in `vite-preview-runtime.ts`); `vite.config.ts` builds both pages.
