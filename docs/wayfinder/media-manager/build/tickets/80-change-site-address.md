## What

Decision 7: changing the address later (for example from `user.github.io/my-site/` to an own domain) updates every address in one go.

- When the path part of the address changes in Site settings, the editor rewrites every root address in the site's text files from the old prefix to the new, as one Undo step, and says how many it changed ★.
- Sites whose prefix does not change see nothing new.

- `@smoke` `tests/native-save/native-subfolder-site.spec.ts`: set a project-site address on a fixture site; links, images and the component loader gain the prefix; the canvas still shows the page; Undo restores.

## Done (2026-10-15)
- **Behaviour.** When the path part of the Site address changes in Site settings (added, changed, removed: `https://user.github.io/my-site/` → `https://example.com/`, and every other way), every root address in the site's text files moves from the old folder to the new one in the same Undo step as the settings. Sites whose folder does not change (no address, a new host with the same folder, `/café/` ↔ `/caf%C3%A9/`) see nothing new.
  - **Question first ★**, in the dialog's footer in place of its buttons: "This updates 9 links in 4 files to the new address. Undo is available." with **Cancel** and **Update links** (focused). Cancel: "Kept the old site address. Nothing was applied." and the field goes back to the old address. No question when nothing would change.
  - **Result ★**: "Site settings applied as drafts. Updated 9 links in 4 files to the new address. Publish to keep them." (Undo: "Undid site settings and the links updated to the new address."); with a sharing copy made in the same Apply: "Social image set as a draft. Updated 9 links in 4 files to the new address." Singular forms say "1 link", "1 file". Like every Site settings result, it is announced through the editor's status live region, which is screen-reader only (see Follow-ups).
  - **What moves** (`src/page-builder/site-address-rewrite.ts`, lazy: imported only when the folder changes): every root address the scanner reads as a link (`scanMediaUrlTokens`: `href`/`src` on any tag, `srcset`, `poster`, meta images, inline and file CSS `url()`/`@import`), `_redirects` sources and destinations, `_headers` path lines, plain root links (`/about/`) and prefixed ones alike, keeping entities, CSS escapes, percent case, queries and `#` as written (the rename's `decodedSource`). Elsewhere (inline scripts, JS, JSON, XML, Markdown, text) only an address naming a page or file of the site, and a bare root path only as a quoted string, an address field's value (`"start_url": "/"`, `action=/about/`) or a Markdown link/image; `split("/")`, `x=/regex/`, prose like `work/<slug>/index.html` and code spans stay. Full addresses on the old address's host inside its folder move to the new host and folder (canonical, `og:url`, `og:image`, sitemaps, robots), the home page too; another project site on the same host and outside links stay; with no old address (or the address removed) full addresses stay. A link already under the new folder is not doubled unless the site has a real folder of that name. `.editor/` and `CNAME` are not read; Site settings' stored default social image moves like the pages' copies of it.
  - **One step, proved**: every text file is read first (the rename's batch reader), the plan is made from a snapshot in slices that yield to the page, the question is asked, then the snapshot and the file list are proved again and inside the guarded edit (the file list as its `guard`, the sharing copy's `live()`). Files move first, then the settings are written in the new address's form (`siteSettingsWithMove`), so nothing moves twice.
