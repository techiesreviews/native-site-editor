## Current Slice

Working:

- Browser-native preview for `.astro-editor/native.json`: persistent sandboxed iframe, HTML/CSS/component patching, shared styles, native slots, nested shadow DOM components, route-preserving source updates, and no Astro build per edit.
- Native preview click-to-select: a plain click on any preview element selects it immediately and opens the owning page/component source plus rendered matching CSS rules from the current document or shadow tree without reloading the frame. The owning file opens with the caret just after the element's start tag, which stays highlighted while the file is edited; the runtime reports element-child indexes and `src/native-source-location.ts` maps them to source offsets through the same browser parser. There is no mode button. Ctrl/⌘+click follows a `#route` link; the runtime's `route` message is read before the stale-render filter in `src/components/native-preview.ts`, as are the other messages that carry a user's action (`text-edit`, `format`, `move`, a `section-drag` cancel), so a click or key that lands while a render requested since is still pending (component styles arriving after the first paint) is acted on rather than dropped; the host checks each against the current source. Messages that describe the runtime's DOM (`select`, `text-selection`, `insert-points`, `structure`, the rects, a drag's start and target) stay filtered and are reported again after the render; a stale drag end, and the cancel the runtime sends when a render replaces the page under a drag, end the drag with "Section drag cancelled" instead of being dropped silently. The preview has no toolbar; the frame fills the pane above the code split.
- Style panel cascade (`shared/cascade.ts`, runtime `matchingRules`, `src/style-cascade.ts`, chips in `renderLinkedStyle`; unit tests `tests/cascade.test.ts`, browser tests `tests/native-preview/native-cascade.spec.ts` over the `fixtures/cascade/*` repositories): the runtime reads every rule matching the selected element from the CSSOM — its file and rule index, tree context (the element's tree with its `style` attribute, `::slotted()` rules of each slot it is assigned to, `:host` rules of its own shadow root), layer path (anonymous layers and import `layer()` wrappers included), the tree's layer order as registered by `@layer` statements and first use, `@media`/`@supports`/`@scope` conditions (evaluated; `@container` counts as possibly applying), order of appearance and declarations with `!important`. The pure `resolveCascade` sorts per property by importance, context, style attribute, layer (reversed for `!important`), specificity (computed from the resolved selector: `:is/:not/:has` max, `:where` 0, nesting as `:is(parent)`) and order, then checks the answer against the browser: each declaration is also set as `!important` in the element's style attribute to read what it computes to, and a winner counts only if that equals `getComputedStyle`; otherwise the property's declarations are "not verified" and nothing is claimed overridden. Rules matching only in a user-action state (`:hover`, `:focus`…) are listed as state rules outside the resting cascade. Chips list rules that win a property first (cascade order), then neutral ones, then fully overridden ones (struck through); each shows its layer, context and condition kinds, and a tooltip lists its declarations as winning, overridden (by which rule) or unverified; overridden declarations are struck through in the editor. With nothing selected, the first stylesheet in the cascade for `<body>` opens beside a page. Scope proximity is not modelled (the computed check catches disagreements).

## Architecture

1. **Editor hosting:** Cloudflare Pages serves `dist` and Pages Functions delegate `/api/*`, `/auth/*`, and `/mcp` to the existing `worker/app.ts` handler. Pages cannot own a Durable Object class, so `native-site-editor-sessions` is a separate Worker owning the SQLite `SessionStore`; Pages binds to it by `script_name`.
2. **Unpublished preview:** source files and browser drafts render instantly inside the editor. Editing does not wait for GitHub, build jobs, or deployments.
3. **User website publishing:** later exporter should generate standalone site files and let each user own a separate Git-backed Pages project. Save-to-GitHub and website deployment remain separate operations.

Relevant limits checked 2026-09-23: Pages Free has 500 builds/month, one concurrent build, 20,000 files/site, 25 MiB/file, and 100 projects/account; Pages Functions share Workers Free request limits; SQLite Durable Objects are available on Workers Free with quota limits; GitHub App user tokens are bounded by both user access and App permissions; GitHub authenticated REST is normally 5,000 requests/hour. Pages Git integration can deploy pushed branches; Direct Upload projects cannot later switch to Git integration, so choose the production project type deliberately. No paid services were enabled.

Sources: [Pages limits](https://developers.cloudflare.com/pages/platform/limits/), [Pages Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/), [Pages bindings and Durable Objects](https://developers.cloudflare.com/pages/functions/bindings/#durable-objects), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [GitHub App user tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Pages Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/), [Pages Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).
